实现 PR：https://github.com/nexu-io/open-design/pull/8683

本指导对应实现提交 `8e165eb9ed2116caa85cc233cfb7e29c0b1ccf5d`。产品行为说明见

## 开测条件与当前移交状态

代码、本地自动化证据及界面截图已提供。**目前尚未提供包含该提交的安装包链接，
也未完成真实云端账号/打包客户端双机验收。** PR 可用于源码测试；正式安装包验收
须先在 Plane 补上对应构建的下载链接、版本、提交 SHA 和平台，不能拿旧版本包验收。
此处不代表已经发布，也不代表 QA 已通过。

准备以下环境：

- A、B 两台设备各自运行独立客户端，使用同一个测试账号、同一个团队工作区。
  同一 daemon 上的两个浏览器页签不能替代双设备。
- 账号具备创建/共享项目权限；A、B 都能在团队项目列表看到由该账号共享的测试项目 P。
  这里的 owner 指项目内容所有者，不要求账号的团队角色一定是 owner。
- 可选 C：另一个团队成员账号，用于只读权限和成员镜像回归。
- 使用可丢弃的测试项目。准备 `index.html`、一个普通文本文件和一个图片，内容标记为
  A1/A2/A3/B1，便于区分完整覆盖、接收和回传。每次继续下一步骤前，确认前一版本
  已发布成功；单纯完成本地保存不等于已发布。
- 记录两端版本、构建 SHA、平台、工作区/项目 ID。日志与截图先脱敏；不要提供
  token、凭据或真实客户项目。数据路径遵循根 [AGENTS.md](../../AGENTS.md) 的
  **Daemon data directory contract**，本指导不另设数据目录。

## 主流程（必验）

各用例开始前，除特别说明外，在 B 点击「恢复更新提示」清除仍有效的 24h 配置，
并确保 A/B 已处于同一个已发布基线。内容标记不是 Hub 的数字版本号。

| 编号 | 操作步骤 | 预期结果与取证 |
| --- | --- | --- |
| Q1 首次打开 | A 创建 P、保存 A1 并共享；B 从未打开过 P，现在从团队列表打开。 | B 自动落地 A1，不出现覆盖确认；可预览、编辑。记录首次打开录像和两端实际文件内容。 |
| Q2 进入页面 | B 已有 A1，退出 P 页面并关闭客户端；A 修改 HTML、文本、图片为 A2 并发布；重新启动 B，打开 P。 | 出现「云端有新内容」。B 确认前仍保留 A1；未勾选 24h，点击「使用云端内容覆盖」后变成完整 A2。不需要先在 B 编辑来触发接收。 |
| Q3 SSE | B 停留在 P 页面；A 发布 A3。 | B 不刷新页面也出现确认，确认前保留旧内容；确认后预览及文件内容更新。记录发布至提示、确认至更新的耗时。 |
| Q4 取消/重试 | 出现新版本提示后点击「暂不更新」；刷新或重新打开同一项目，再点「检查云端更新」。 | 取消不改本地内容，同一版本不会仅因重新打开重复提示；手动检查可再次提示。A 再发布另一个版本时仍会提示。 |
| Q5 24h | B 在确认框勾选「24 小时内本项目不再提示」并确认成功；A 再发布新版本。 | 后续版本在 B 自动覆盖，不弹确认；出现「恢复更新提示」入口。这是允许完整覆盖，不是仅隐藏弹窗或暂停同步。 |
| Q6 重启/隔离 | Q5 成功后重启 B；A 再发布 P。另建已缓存旧内容的项目 P2，在 A 发布 P2 的新内容。 | B 的 P 仍自动接收，P2 仍需确认。A 的同项目不会继承 B 的配置。切换测试账号/工作区时也不继承旧配置。 |
| Q7 重设/到期 | B 点击「恢复更新提示」，A 发布下一版本。另用一份 24h 授权观察其实际到期，或使用开发侧受控时钟验证边界。 | 重设后的下一版本再次提示；到期后的下一版本也需确认。不要把修改操作系统时钟作为唯一证据；精确到期边界已有单测，真实 24h 观察未做则标为待观察。 |
| Q8 串行续做 | B 接收后编辑为 B1 并发布；A 接收 B1 后继续编辑。包括 A 关闭、B 编辑发布、A 重开的组合。 | 两端按上述确认/24h 规则接续；接收动作本身不产生新的发布，后续实际编辑可以发布，不出现旧内容自动覆盖回去或不断新增版本。若加入 C，C 的只读镜像也应收到 B1。 |
| Q9 HTML 历史 | B 先有本地 A1，再确认接收 A2；打开 HTML「版本」面板，查看「云端同步」来源，恢复旧 A1。 | 同步前后的 HTML 版本可查看；恢复后实际 HTML 为 A1，并可发布给其他端。不会要求云端下载 A 的全部历史，也不承诺文本/图片/整个项目可恢复。 |
| Q10 知情完整覆盖 | B 有尚未发布的本地公共文件改动，A 发布不同内容；B 明确确认，或已有有效 24h 授权时接收。 | 按授权使用远端快照完整替换公共内容；远端已删除的公共文件本地也应删除。不存在自动合并/保留两份的要求。仅在可丢弃项目中验证。 |

## quick fail 与权限（必验）

| 编号 | 操作步骤 | 预期结果与取证 |
| --- | --- | --- |
| Q11 生成/上传冲突 | B 正在执行生成或实际上传时，尝试接收 A 的新版本。需确保任务仍在运行；上传场景可在受控环境限速。 | 明确提示「项目正在生成或上传，请完成后再更新」，不并发覆盖。任务结束后手动检查可再尝试；不要求 BUSY 后自动重试。 |
| Q12 接收时写入 | 在受控慢下载中，尝试从另一个入口发起 B 的文件写入/新生成。 | 返回 PROJECT_BUSY，不把写入混入接收过程。读取/评论权限不因接收被一并关闭。此边界已有 daemon 单测；难以人工制造时由开发提供受控环境取证。 |
| Q13 网络/下载失败 | 先保持 A/B 身份有效，再在 B 确认下载过程中断网或令资源服务失败。 | 显示失败，不把失败标为已同步；未完成替换时旧内容保留，失败确认不能新授予 24h。恢复网络后手动检查可重试。记录失败阶段和耗时，不允许无限等待。 |
| Q14 撤销权限 | 提示出现后，由管理员取消共享或移除 B 所用测试账号的访问，再尝试确认。下载中撤销的精确时序用受控环境补测。 | 拒绝接收，不能仅凭已出现的弹窗继续覆盖；账号/工作区错误也不能接收。注意该场景 A/B 为同一账号，移除账号可能同时影响两端。 |
| Q15 本地私有条目 | 在测试 P 的本地目录准备 `.git`、`.file-versions`、私有配置及嵌套私有条目，执行同步。 | 私有条目不被远端替换；HTML 历史仍可用。若远端将含本地私有条目的目录改成普通文件，则 quick fail，旧内容仍保留。路径操作由开发协助，避免改到用户真实目录。 |
| Q16 范围/成员回归 | 检查个人未共享项目、导入文件夹以及 C 的成员项目。 | 个人未共享项目不被自动纳入；导入目录不执行 owner 云端覆盖。C 保持现有成员只读接收机制，不能调用 owner 确认 API 或改写 owner 文件。 |

## 开发协助的确定性检查

旧 head 确认、下载中撤权、上传 BUSY、精确 24h 边界无需仅靠手速。优先使用已有
自动化证据，QA 需要复核时由开发提供受控 fixture；不直接改生产 SQLite、权限或时间。

CLI 与 UI 使用同一接口。使用与被测客户端对应的 `od` 和 daemon，填入测试项目、
工作区及当前成员 ID；JSON 输出中的 `latestVersion` 才是确认所需的数字版本：

```sh
od collab check "$PROJECT_ID" --workspace "$WORKSPACE_ID" --workspace-member "$MEMBER_ID" --json
od collab accept "$PROJECT_ID" --version "$OFFERED_VERSION" --workspace "$WORKSPACE_ID" --workspace-member "$MEMBER_ID" --json
od collab dismiss "$PROJECT_ID" --version "$OFFERED_VERSION" --workspace "$WORKSPACE_ID" --workspace-member "$MEMBER_ID" --json
od collab ask-again "$PROJECT_ID" --workspace "$WORKSPACE_ID" --workspace-member "$MEMBER_ID" --json
```

授权 24h 使用 `accept --dont-prompt-24h`。指定 daemon 时附加 `--daemon-url "$DAEMON_URL"`。
先 check 记录版本，再由 A 发布下一版本，用旧数字 accept：必须重新提示最新版本，
不能把旧确认视为对新版本的授权。检查状态应以实际文件、`update.state`、
`localVersion/latestVersion` 和 `autoApplyUntil` 联合判断，不能只看旧 `syncState` 字段。

## QA 回填与退出条件

逐项回填 Q1–Q16 的 Pass / Fail / Blocked / 未执行；引用已通过的开发证据时标为
“开发证据复核”，不要写成真实环境通过。回填包含：被测包/版本/完整 SHA、两端平台、
测试账号与工作区/项目 ID（脱敏）、操作时刻、预期/实际内容、必要录像、版本/head
记录及脱敏日志。失败时保留可恢复测试现场，不清理或继续编辑覆盖证据。

接受条件：必验主流程、权限和 quick fail 用例通过或有明确复核证据；真实账号的
owner resource 下载与打包双机接续必须有实际通过记录；未做的真实到期/大项目等
观察显式记录并由验收方判断是否影响签收。安装包缺失或真实资源鉴权拒绝则标
Blocked 并附证据，不能以本地 mock 通过代替。验收结果回填 Plane，当前事项不预先关闭。
